## Findings

1. **[P1] Bind the artifacts checked by producer reports into final release validation.** `tools/validate_release.py:45` calls require_report without root; `run_stage:115–124` hashes only declared expected_reports/expected_files, not the producer report's artifact_hashes. `validate_release:141–151` verifies these wrapper hashes, then freshly hashes expected files without comparing them to the producer's validated bytes. The R4 media/doc stages declare no expected files (`tools/build_r4_candidate.py:53,56`). Therefore replacing a PDF or MP4 after its successful stage but before validate_release succeeds yields a new PASS proof for unchecked bytes. Per-part/section STEP hashes have the same transitive gap where they are only in the export producer report; manual generation currently checks export hashes, but changes after that check remain possible. Packaging reruns the same incomplete validation, and review bundles share the problem. Validate nested producer hashes at stage completion and again at release/package time, or merge all producer artifact hashes into the immutable wrapper contract. Require the expected artifact set, not merely whatever hashes a producer supplies. Regression: mutate PDF/video/per-part STEP after a passing stage; both release and review packaging must reject it.

2. **[P1] R4 reports bypass the actual result-field schemas.** `tools/validate_release.py:42–46` returns immediately for every reports/r4_* report after checking context/status/completed-check strings. It does not require actual result fields or verify their values. For example a source-matched r4_blender report with all required completed_checks but blend_reopened=False/glb_reopened=False/ids_preserved=False is accepted; so is a report containing only ctx.report('PASS', REQUIRED_STAGES['r4_blender']) with no reopen fields or artifact hashes. The legacy branch explicitly checks these booleans, but the new production pipeline bypasses it. Add typed R4 schemas for each canonical stage, including required artifacts and actual true/count/defect fields; completed_checks alone must not substantiate the result. Add negative coverage for matching-provenance R4 reports with missing/False fields, incomplete artifact sets and contradictory defect payloads.

3. **[P2] Tool resolution differs between probing, provenance and execution.** `tools/doctor.py:probe` supports the project-local portable Blender fallback; `tools/build_context.py:55–58` and `tools/check_failure_modes.py:24–25` do not. An otherwise supported portable installation can pass doctor/preflight but then fail failure_modes, or reach build_r4_scene with tool_versions.blender={'status':'NOT_AVAILABLE'} and fail its sha256 lookup. Separately `tools/check_r4_viewer.py:17` always launches Playwright channel='chrome', ignoring BM1_CHROME_EXE even though doctor/context record that override. The browser actually tested can differ from the executable reported in provenance. Use one resolver for all three layers and launch the resolved executable_path. Verify the portable-Blender/no-PATH route and a nondefault Chrome path without conflating a missing tool with a valid alternate installation.

4. **[P2] Standalone media generation can certify stale frames as current-source output.** `tools/finish_r4_media.py:12–16` creates a fresh context and checks only that expected frame filenames exist. It never requires the same-run Blender report or verifies frame source/hash provenance. `blender/build_r4_scene.py` does not include the animation frames in artifact_hashes. After a source change, direct finish_r4_media can encode prior-source frames and emit a current-input/current-code PASS report. The pipeline's cleared output directory helps the orchestrated path but does not satisfy the direct-entry stale-cache requirement from original finding 4. Bind the complete frame set to the Blender producer report/manifest and require its current context and hashes before encoding; reject old or changed frames in a direct-entry regression.
