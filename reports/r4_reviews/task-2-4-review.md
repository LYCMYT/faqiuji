## Important findings

1. **[P1] The new runner cannot consume its own service report.** `tools/rebuild.py:37` declares `reports/service_validation.json` an expected report, but `tools/check_service.py` writes a JSON array of cases. `tools/validate_release.py:56–57` unconditionally calls `.get()` on it. Both core and full builds therefore stop with AttributeError even when every service case passes. Introduce an explicit service-report adapter/schema (requiring every case's geometric_path_passed=True), or migrate the producer and all consumers to a provenance-bearing mapping. Verify the successful service-report path as well as collision rejection.

2. **[P1] Missing/malformed check results can be converted to current-run PASS.** `tools/validate_release.py:55–67` accepts `{}` (and RUNNING or unknown statuses) for most report names: missing status/errors/unresolved_pairs take the successful defaults. It never verifies report run_id, source hashes, scope or completed_checks before minting the wrapper's PASS. Caller-provided completed_checks are credited without proof from the report. Require a typed per-stage schema and explicit success, then validate context and required completed checks; adapt legacy reports explicitly instead of treating absent fields as success. Add zero-exit fault cases emitting `{}`, wrong source/run/scope, RUNNING, missing collision counts, and malformed field types. `require_report` should also reject unexpected stage when the requirement is for a specific stage.

3. **[P1] Release validation has no production caller or fixed acceptance contract.** `tools/rebuild.py:47–54` runs many stages with no expected reports/files and writes build PASS directly; it never calls validate_release or writes a release proof. `tools/validate_release.py:75–83` accepts caller-selected empty requirements/expected_files, and checks only nonempty bytes for expected files. `tools/package_delivery.py` trusts a supplied proof's self-described context and nonempty hash map, without requiring the complete prescribed stage/artifact set. Consequently there is no supported complete build→validated proof→package path, and an incomplete proof with a single unrelated file is structurally sufficient. Define the required full-build stages and artifacts centrally, validate every stage against that contract, persist the proof after the final checks, and have packaging enforce that exact contract. Keep core diagnostics ineligible. R1 assembly/section STEP completeness and actual R1 Blender/GLB fields must be included, not inferred from process exit.

4. **[P1] Standalone report/export paths still allow stale artifacts and leave old final PASS visible after failure.** Only declared expected_reports are invalidated by the runner; most late stages declare none (`rebuild.py:47–52`). `tools/final_report.py` validates current-run unit tests but reads STEP, Blender, service, viewer/PDF/parameter reports directly; only static/motion source hashes/run are compared. Standalone final_report can therefore combine fresh tests with old roundtrips, and earlier failed rebuilds leave old acceptance_report/validation/R3 delivery files untouched. `tools/check_service.py` and `tools/make_section.py` import BREP files without require_cache; only the collision consumer received the cache guard. Centralize provenance validation for all cache/report consumers, invalidate final release/summary targets at build start, and atomically publish new successful results only after same-run checks. Add direct-entry stale-cache/report regressions; subprocess wrapper coverage alone does not meet the single-script requirement.

5. **[P2] The immutable-input boundary excludes the project's original input evidence.** `tools/input_manifest.py:classify_paths` protects all data/ and evidence/, but omits input/. The existing reports explicitly identify input/ as the preserved original task/source material, and package_delivery includes it. Changes to these records are neither blocked by snapshots nor included in input_sha256. Include original input files in the authoritative/evidence classification (document any intentional exclusions), and test a nonempty original input record through rebuild/PLAN generation.

6. **[P2] Provenance omits actual release dependencies and tool identities.** `tools/build_context.py:code_paths` hashes only Python in six folders; viewer HTML/JS, templates and other consumed source assets are absent. `tool_versions()` records the invoking Python packages but no actual selected Blender, ffmpeg/ffprobe or PDF/browser tool versions. `tools/doctor.py` reporting these separately does not bind them to the build context or invalidate an old proof. A changed viewer/template or selected Blender binary can retain the same context fingerprint. Include consumed non-Python assets and the actual executable/version identities in the relevant scope fingerprints, and implement the approved-environment policy or explicit unknown/block status required by task 3.
